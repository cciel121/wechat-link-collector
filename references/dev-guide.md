# 开发与自检指南

> 这是 `SKILL.md` 的深度补充材料。只在**要改脚本**时才需要读。

## 1. 实测数据（微信 3.9.12.55 + Chrome，某公众号 103 篇全量）

| 项 | 实测值 |
|---|---|
| 单篇耗时 | 约 6~8 秒 |
| 103 篇总耗时 | **642 秒（约 11 分钟）** |
| 链接成功率 | **103/103**，103 条 URL 互不重复，全部是 `/s/xxx` 永久短链 |
| 标签页自动关闭 | **103/103** |

- 上一轮 20 篇的小样本里曾有 1 个标签页因抢前台失败被安全守卫正确跳过
  （那是设计行为，不是 bug）；全量跑的第二轮起是 100%。
- 有 1 篇**首次因窗口被完全遮挡读不到 URL**，用 `--skip 35 --max 1` 单独重试即成功
  —— **按序号重试是有效的补救手段**，不要因为一篇失败就把整批作废。

### 1b. 折叠分组布局（`collect_grouped_layout.py`，2026-09-22 实测）

| 项 | 实测值 |
|---|---|
| 单篇耗时 | **约 1.9 秒**（30 篇 56 秒） |
| 30 篇试采 | **30/30 成功**，全为 `/s/xxx` 永久短链 |
| 该号当时**已加载**的可见条目 | **485 条**（滚动到底后仍在继续加载） |
| 「余下 N 篇」展开 | **有效**：实测点一次同页 33 → 37 条；整页 19 组一次点完（10 组约 12s），展开后 **143 篇全部可见**、零残留标记 |
| 位置配对校验 | 展开后 **143/143 通过**（第 i 个阅读数元素名字 == 第 i 条解析结果） |

- 逐篇耗时随布局/机器浮动 **1.9–4.5 秒**；采集期间**不能动键鼠**。
- ⚠️ **「可见条目数」≠「该号文章总数」**：折叠在「余下 N 篇」里的那些根本不在页面正文里，
  **只有展开后才数得到**。同一窗口先后两次的实证（2026-09-22）：
  - 未展开：**58 篇可采 + 19 个折叠标记（累计折叠 85 篇）**；
  - 展开后：**143 篇全部可见**，一次点完 19 组；
  - 更早那次未展开的 30 篇试采，日期组分布是
    `9月17日:8 / 9月10日:7 / 9月1日:3 / 8月26日:1 / 8月22日:3 / 8月14日:3 / 8月7日:3 / 7月31日:2`
    —— **4 个组恰好各 3 条**，正是「每组只展开 3 篇」的指纹；展开后重采，
    **前 30 条里有 8 条是那批完全没有的**，且旧版照样"走"到了 7月31日、白占 8 个名额。
  → 所以脚本**默认先展开**，跑完再数一遍剩余折叠标记报警（`folded_markers()`）。
  → 推论：**任何「未展开」产出都不能当作该号的最近 N 篇**，哪怕报告看上去完全正常。
- 该布局下**能读到多少条同样取决于页面加载了多少**：不滚动只会拿到首批，
  **别把首批说成全量**（与平铺布局同一个坑）。

## 2. 改脚本后必做

改任何脚本后跑 `python scripts/selftest.py`，必须 **全部通过（当前 134 项 / 11 组）**：

| 组 | 项数 | 覆盖 |
|---|:---:|------|
| 1 | 6 | `clipboard_watch` 的链接识别与去重 |
| 2 | 8 | `analyze_capture` 的链接提取与列表接口判定（jsonl） |
| 3 | 5 | Fiddler `.saz` 解析 |
| 4 | 6 | `clipboard_watch` 主循环落盘 + **跨脚本联调**（产物喂分析器不能变 0 条） |
| 5 | 1 | mitmproxy addon 语法 |
| 6 | 5 | `collect_wechat_uia` 编译 + 产物契约 |
| 7 | 12 | `profile_parse` 索引解析规则（含「标题里带『月』『日』不能误判成日期」这条真实边界） |
| 8 | 12 | 路径 A+++ 两处要害：**标题匹配**、**多标签页时挑对目标文档** |
| 9 | 23 | `make_link_report` 报告合成（顺序以索引为准、缺失必须列出、空输入必须报错、**索引缺失必须出声**、**大标题自动取账号名**、**`.md` 与 `.html` 同源/标题转义/`--no-html`**、**同名标题不许去重**） |
| 10 | 23 | **`--doctor` 环境预检判定**（含「20 篇」误判与「4 标题判平铺」的回归）、**依赖清单与启动器措辞**（含**自动扫描**：凡是顶层 `import pywinauto` 的脚本都必须登记进 `requirements.txt` 的必需清单——2026-09-22 真漏过折叠布局采集器）、**`links.jsonl` 文档字段清单 == 实际写盘字段**（真缺陷：曾漏写 `likes`/`page_title`）、**SKILL.md 正文中文字数 < 5000**（超了就往 `references/` 搬——这条加之前，正文曾静默涨到 5408 而无人出声） |
| 11 | 33 | **折叠分组布局**：`parse_grouped` 从正文抠标题/日期/阅读数、`absolutize_date` 相对日期换算（含「标题里的 `2026年9-10月` 不当日期组头」「跨年 `星期X` 必须带年份」）、**漏采闸门 `folded_markers`**（还剩几个「余下 N 篇」、累计折叠几篇）、**截断告警 `truncation_info`**（`--max` 把某天从中间切断）、**索引 ↔ 链接同条数** `index_rows_from_store`（分批续采时索引不许只剩最后一批）、**接线检查**（采集器默认展开 / 闸门真的被调用 / 写索引走纯函数 / `--expand` 仍是只展开就退出） |

历史教训都指向同一类失败——**单脚本自检发现不了交界处的错**：两个脚本各自全过，
拼起来照样静默返回 0 条。**新增或修改跨脚本数据契约时，必须同时往对应的联调组里加断言。**
（2026-09-22 新案例：采集器写索引时只写**本次**的 `records`，分批续采就变成
「索引 40 条 / 链接 70 条」——报告照样生成、排序却是错的，**没有任何地方会出声**。
已改为 `index_rows_from_store(store, order)` 按累计内容出索引；自检第 11 组 6 条断言钉住，
实测「先 30 再 `--skip 30 --max 40`」两批合并后索引↔链接**逐条 0 处不一致**。）

> `selftest.py` **不需要 pywinauto**：实测用裸 `python`（无 pywinauto）跑，11 组全跑、
> 134/134 全过、零跳过。
>
> ⚠️ 这也意味着**第 11 组的被测函数必须待在零 UI 依赖的 `profile_parse.py` 里**。
> 一旦让自检去 `import collect_grouped_layout`，pywinauto 会被拉起、缺依赖时 `sys.exit`
> 会**顶掉整个自检进程**，第 11 组连跑都跑不到（这个坑已踩过一次）。
> 需要验证采集器"接线对不对"时，**读源文件文本**（见第 11 组的 `--no-expand` /
> `folded_markers(` / `truncation_info(` 三条断言），不要 import 它。

## 3. 无法离线自检、只能真机回归的部分

- 真实点击/打开链路（需要真实微信窗口 + 系统默认浏览器）。
  改 `collect_via_browser.py` 后至少跑一次 `--doctor` 和 `--max 3`；
- 改 `collect_grouped_layout.py` 后同样跑一次 `--doctor` 和 `--max 3`，
  并**跟一次「首篇标题校验」的输出**（对不上会以退出码 3 停下，这是设计行为）；
- 改 `collect_wechat_uia.py` 后跑一遍 `scripts/fixtures/` 夹具，两种打开模式都要过。
